# GX-TXT Module Plot Configuration API v1

SPDX-License-Identifier: GPL-3.0-or-later

## Purpose

A scientific module must declare its plots and the parameters that the user may customize. The GUI must not contain plot controls hard-coded for a specific analysis.

Plot configuration is part of the module descriptor and is therefore generated by the same Standard Module API used for calculation parameters and input bindings.

## Descriptor example

```ini
[graphs]
ids=curvefit.family.overlay
rerender=standard_octave

[graph.curvefit.family.overlay]
name=Measured vs fitted curve family
file=01_curve_family_fit.png
supports_legend=1
legend_editor=standard
legend_placements=inside;above;below;left;right;manual
legend_layouts=row;stacked;wrapped
config_fields=title;x_label;y_label;show_measured;show_fitted;marker_size;line_width;legend_mode;x_min;x_max;y_min;y_max

[graph.curvefit.family.overlay.config.title]
type=string
label=Plot title
default=Curve Family Fitting - measured vs fitted

[graph.curvefit.family.overlay.config.show_measured]
type=boolean
label=Show measured points
default=1
```

Supported widget types currently follow the standard descriptor GUI: `string`, numeric values represented as strings, `choice`, and `boolean`.

## Manifest

Each module plot receives its own section:

```ini
[module_plot.curvefit.family_global.curvefit.family.overlay]
title=6BX7-GT characteristic curves
x_label=Anode voltage [V]
y_label=Anode current [mA]
show_measured=1
show_fitted=1
marker_size=4
line_width=1.6
legend_mode=family_only
x_min=
x_max=
y_min=0
y_max=
```

## Runtime contract

The framework copies the plot configuration into the module runtime file:

```ini
[plot.curvefit.family.overlay]
...
```

The calculation renderer and rerender entry point receive exactly the same settings. Rerender therefore changes presentation without repeating the numerical fit.

## Separation of responsibilities

- `[graphics]` contains generic renderer/server properties shared by modules: dimensions, fonts, toolkit, background, global grid and legend defaults.
- `[module_plot.<module>.<plot>]` contains semantic/content choices owned by a specific plot: title, axis labels, which series are shown, module-specific line/marker choices and optional axis ranges.
- The **Plots** tab manages already-produced plot artifacts, rerender, clone, legend placement, export and print.
- The **Analysis** tab exposes descriptor-generated plot configuration before calculation/rerender.

A new module can therefore add plot controls by editing only its descriptor and renderer; no core Tcl GUI branch is required.

## Standard legend editor contract

A descriptor-defined plot that has a legend and wants the common Plots-tab editor declares:

```ini
[graph.<graph-id>]
supports_legend=1
legend_editor=standard
legend_placements=inside;above;below;left;right;manual
legend_layouts=row;stacked;wrapped
```

The common editor deliberately separates **where** the legend is placed from **how** its entries are arranged.

### Placement

`placement` is one of:

- `inside` — inside the data axes; `location` chooses the inside preset;
- `above` / `below` — external horizontal band;
- `left` / `right` — external vertical band;
- `manual` — free overlay position; `manual_x` and `manual_y` are the legend center in normalized figure coordinates;
- `none` — hidden.

`location` is therefore an **inside preset only** (`north`, `northeast`, `east`, etc.). It does not compete with `below`, `above`, `left`, or `right`.

For external placements, `alignment` is independent:

- `start` — left for above/below; top for left/right;
- `center` — centered;
- `end` — right for above/below; bottom for left/right.

### Entry layout

`layout` is independent from placement:

- `row` — all entries in one row;
- `stacked` — one vertical column;
- `wrapped` — several rows using `columns` entries per row;
- `auto` — framework default (`row` for above/below, `stacked` otherwise).

Examples that are all valid:

```text
below + row
below + wrapped + columns=4
right + stacked
inside + row
manual + wrapped + columns=3
```

The editor also manages background, border, border color, font size, external margin, and manual center coordinates. Legend font size always uses the global plot font unit (`px` or `pt`); it has no independent unit.

### Renderer contract

The module renderer must call the centralized helper:

```octave
gxtxt_plot_legend(labels, plot_config, graph_id)
gxtxt_plot_legend(handles, labels, plot_config, graph_id, runtime_cfg)
```

The handle-aware form lets a module choose exactly which plotted objects appear while retaining common placement and styling. Calling Octave `legend(...)` directly bypasses the framework and is non-conformant for a plot declaring `legend_editor=standard`.

For GNUplot, v0.6.9 uses a common legend-axes renderer rather than relying on native GNUplot legend `Position` during `print()`. The legend is drawn in its own figure-normalized axes, so `inside / above / below / left / right / manual` and `row / stacked / wrapped` are deterministic and independent. The data axes are resized only when an external band needs additional room.

## Persistence and runtime delivery

The editor state is stored in Manifest Format 2 under `[plot.legend.<graph-id>]` and copied into `[legend.<graph-id>]` in `runtime.ini` before every native rerender.

New fields are:

```ini
placement=below
layout=wrapped
alignment=center
location=northeast
columns=4
```

`mode` and `orientation` may still be present as migration aliases for older v0.6.x manifests, but new code gives precedence to `placement`, `layout`, and `alignment`.

`Save and rerender plot` regenerates `runtime.ini`; rerender therefore always receives the current presentation state without repeating the numerical fit.

## Font-unit contract

All common plot font sizes, including plot-specific legend overrides, use `plot_font_unit`:

- `px` means final-PNG pixels and is converted to Octave points using output DPI;
- `pt` means typographic points.

Changing the GUI unit converts the displayed numeric values so the rendered physical size remains unchanged. At 200 DPI, 12 px becomes 4.32 pt and converts back to 12 px.

## Standard annotation editor contract

A plot opts into the non-destructive annotation layer independently from legend support:

```ini
[graph.<graph-id>]
supports_annotations=1
annotation_editor=standard
annotation_types=text;line;arrow;rectangle;ellipse
annotation_coordinate_spaces=figure_norm
```

The module continues to produce only its base plot. The framework owns the editor, JSON persistence, preview overlay, annotated export and automatic Print/PDF composition. See `PLOT_ANNOTATION_API_v1.md`.

## v0.7.1 — Graph Provider API and legend sizing

Plot Module API and Graph Provider API are complementary. `[graphs].ids` is now formally the module's **offered graph catalog**; the experiment selects which offerings are active. See `GRAPH_PROVIDER_API_v1.md`.

A graph-specific legend font may override the global unit:

```ini
[plot.legend.curvefit.family.overlay]
font_unit=pt
font_size=9
```

`font_unit` is `px`, `pt`, or blank/inherit. The global unit remains `graphics.plot_font_unit`.

GNUplot legend geometry measures each label and each effective column. If a requested `row` or wrapped column count cannot physically fit inside the available figure/axes width, the renderer automatically reduces the effective column count and reports the change in the analysis log. This prevents the legend border and labels from being clipped by the right edge of the PNG.

The global output DPI is `graphics.analysis_png_dpi`; modules must not duplicate DPI as a private calculation parameter unless a scientifically distinct raster output explicitly requires it.


## Font units and DPI

The global graphics profile owns default output DPI and typography. Font sizes may use `px` or `pt`. The legend has its own effective font unit (`inherit`, `px`, `pt`), and the per-plot legend editor places the size field and unit selector together.

A module-wide graphics override can replace global DPI/typography only when explicitly enabled. A per-plot legend override is applied after the module override.

[ax_left,ax_right] = gxtxt_plot_dual_y_axes(fig,plot_config)

supports_region_selection=1

## GX-TXT 0.9.7.11: persistent plot variants

A graph_id is the fixed Graph Provider plot **type**. An optional variant_id identifies one persistent independent configuration of that type. The historical configuration is the base, with an absent/empty variant_id. Existing graph IDs, manifests and plugins need no migration.

A descriptor opts in per graph:

~~~ini
[graph.plot.dataset.xy]
file=01_dataset_xy.png
supports_variants=1
~~~

The generic Analysis GUI offers Variants... for an opted-in graph; the Plots GUI can open the same manager from a selected artifact. The framework generates the editor from declared graph configuration fields, module binding roles and common graphics fields. Existing Plots actions edit the selected variant's axes, Y1/Y2/Z Level Scale, legend, annotations and region.

Public Tcl operations in Plot Module API v1:

~~~tcl
::GX::plotVariantSupports module_id graph_id
::GX::plotVariantCreate module_id graph_id ?source_variant_id?
::GX::plotVariantDuplicate module_id graph_id variant_id
::GX::plotVariantIds module_id graph_id
::GX::plotVariantField module_id graph_id variant_id field
::GX::plotVariantSet module_id graph_id variant_id {title text enabled 1}
::GX::plotVariantConfigSet module_id graph_id variant_id key value
::GX::plotVariantConfigGet module_id graph_id variant_id key
::GX::plotVariantBindingSet module_id graph_id variant_id role dataset_id variable_id
::GX::plotVariantBindingGet module_id graph_id variant_id role
::GX::plotVariantGraphicsSet module_id graph_id variant_id field value
::GX::plotVariantGraphicsGet module_id graph_id variant_id field
::GX::plotVariantArtifact module_id graph_id variant_id
::GX::plotVariantDelete module_id graph_id variant_id
~~~

Create copies current base presentation, bindings where resolvable, and base Graph Series. Duplicate copies the chosen variant. IDs are monotonic p0001, p0002, etc.; deletion never renumbers or reuses an ID. The title is a visible configuration name, independent of the graph ID and artifact. The plot-specific title field controls text drawn in the PNG.

Bindings persist dataset_id + variable_id. The current name is resolved when a render is prepared; Use=no retains the binding and produces an explicit unavailable-variable error until the data can be restored. Graph Series API v1 accepts an optional variant argument for independent multi-dataset series. The normal Graph Series absence remains the legacy base. A variant with explicit Graph Series renders those series; otherwise the framework projects its X/Y/Y2 stable bindings into series for the renderer. Other binding roles such as Z remain per-variant and use the primary dataset for their graph type.

Manifest Format 2 adds plot_variant_api, plot_variant_counter, plot_variant and plot_variant_region sections. Existing axis/legend/Level Scale serializers store the variant state under the internal key graph_id.variant_id. The public graph ID remains the descriptor value. The variant runtime projects this state onto the original graph ID, so an unchanged plugin renderer still receives its declared plot, axis, legend and level sections. It receives a plot_variant section with graph_id and variant_id. Plugins that do not opt in continue to use the unchanged base runtime.

Artifacts reside under analysis/<module_id>/variants/<graph_id>/<variant_id>/<declared-filename>. Each variant has its own runtime.ini, render_cache.mat, summary, graph geometry sidecar and generated PNG. The base stays under analysis/<module_id>. Framework annotation storage follows the selected artifact path; export and print operate on that path. The plugin only declares PNG output; combined print PDF and exported copies follow the existing Plots services, and SVG is not declared by plot.dataset.

The analysis queue runs enabled variants as separate jobs. A presentation-only rerender uses that variant's cache when its saved data fingerprint and cache are current. Changing dataset/variable IDs, source bytes or module preparation configuration schedules a full preparation. The standard wrapper records the fingerprint only after successful output-contract validation. Rerender of one variant does not write another variant's artifact. Module/global graphics remain shared defaults; explicit per-variant graphics fields override them for that job.

Plot Region Selection API v1 and Dataset Selection API v1 carry the optional producer variant as described in their contracts. Viewer Provider remains separate.

A variant graph descriptor may declare preparation_fields as a semicolon-separated subset of its config_fields. These fields enter the framework data fingerprint and force preparation when changed. Other plot fields are presentation-only for cache selection. For example, plot.dataset.xyz declares preparation_fields=plot_type because its 3D preparation depends on that choice. Plugins opting into variants must declare every plot-specific preparation field.


## GX-TXT 0.9.7.12 Z Level Scale

Variants clone, persist and project Level Scale state for Z as well as Y1/Y2.
The base graph retains its independent Z state and default linear display.
Presentation-only Z changes are eligible for cache rerender; the prepared

## Bundled plot.dataset 1.1.1 in GX-TXT 0.9.7.15

The protected CORE module uses active Graph Series for both base and variant
2D graphs. A graph with no active series retains its legacy X/Y/Y2/Additional
Series compatibility path. Series use dataset-scoped stable variable IDs,
independent source datasets, enabled/order state and resolved scientific
metadata. The module checks compatible X meaning/units, applies per-series
reduction and non-finite filtering, rejects unsupported implicit temporal
alignment, and keeps separate cache fingerprints for `xy` and `xy_region`.
The 3D graph retains its own X/Y/Z(/Family/Color) bindings. The shared
Multi-Y Axis Plot API owns GNUplot dual-Y geometry; the module does not
implement its own overlay-axis correction.

## Script Bridge operations (GX-TXT dev-037)

These operations discover existing persistent Variants without mutating another provider’s state. `variant_artifact` returns the public artifact path; `variant_field` accepts an optional default, which is the empty string when omitted. A Variant remains owned by its provider and is deleted through the public Plot Dataset lifecycle where applicable. Both Octave/MATLAB and Python call these names through `gxtxt_api_call(API_ID, operation, arguments)`. Arguments are positional and are passed to the named public Tcl procedure.

| Script operation | Public Tcl mapping | Positional arguments | Result |
| --- | --- | --- | --- |
| `supports` | `::GX::plotVariantSupports` | `module_id`, `graph_id` | integer `0` or `1` |
| `variant_ids` | `::GX::plotVariantIds` | `module_id`, `graph_id` | cell of IDs |
| `variant_field` | `::GX::plotVariantField` | `module_id`, `graph_id`, `variant_id`, `field`, `default` (optional) | field value |
| `variant_artifact` | `::GX::plotVariantArtifact` | `module_id`, `graph_id`, `variant_id` | artifact path |

Direct Variant creation, deletion, field/configuration/binding/graphics
mutation, and provider-owned configuration/binding/graphics getters remain
host-only for general scripts. Scripts can discover IDs, public fields and
artifact paths through the four registered read-only operations. Nested Tcl
dictionaries and lists returned by these operations are normalized for script
clients.
