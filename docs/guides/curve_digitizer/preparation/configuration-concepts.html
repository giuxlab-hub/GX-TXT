Know which state you are changing

A source filter, a shared preference, a scientific configuration and a published Dataset have different identities and persistence. Keeping those roles explicit makes a saved workflow easier to understand and reopen.

A Dataset namespace filters choices without rebinding the source

The vendor manual describes Dataset namespaces as organizational groups for canonical Datasets. They are distinct from filesystem directories and Session Workspaces. A namespace selection narrows the compatible Image Dataset choices; an all-namespaces selection shows compatible images across the Session.

Changing that filter does not move or rename a Dataset and does not change a saved configuration's bound source ID. A source can be hidden by the current filter while remaining the configuration's source. Do not select a similarly named visible image merely to make the selector look populated.

The documented catalog refresh tracks revisions and updates available choices. Refreshing a list does not authorize replacing an old source binding or applying its calibration to different bytes. Missing or changed sources need their real diagnostic and deliberate recovery; preserve the existing points and calibration rather than guessing a replacement.

Keep a selected browser item, an explicitly confirmed source binding and a verified source identity separate in the explanation. For published Quality data, also retain the provider-versus-CORE observation qualification; a provider field alone does not establish current-byte verification.

A named configuration has a stable scientific identity

A Digitizer configuration is a Session Interactive Document associated with one source image. It holds scientific axes/calibrations, curves and ordered points, relevant per-configuration state, publication targets and notes. The display name helps you find it; its stable identity distinguishes it from another configuration with similar content.

Several configurations can use the same image with different scientific regions or calibrations. A source binding is still meaningful only for its actual raster. The manual blocks changing a calibrated configuration to an unrelated source; use the deliberate new/duplicate/reset workflow appropriate to the real accepted version.

Do not confuse a configuration identity with a curve identity, calibration measurement identity or calibration transform fingerprint. The same mapping can occur in two different measurement realizations. See publication objects and calibration grouping.

Shared defaults and configuration science have different owners

Which state an operator intends to change
StateDocumented scopeInterpretation
User defaultsShared module preferences managed by the normal CORE configuration service.A starting preference, not a new calibration of every existing configuration.
Session overridesExplicit shared preferences in the current Session, with normal CORE inheritance/precedence.An inherited value and an explicitly overridden value can look the same while having different scope.
Configuration-owned scientific stateAxes, measured references, points, source bindings, names and publication targets in the selected Interactive Document.Scientific meaning remains attached to the actual configuration and source.

For example, a scale-bar tick convention, default length or full-image Y-direction preference applies to subsequent calibration actions. Changing a default does not retroactively rescale an accepted measurement. Likewise, hiding a saved scale overlay changes its presentation; resetting physical scale is a separate explicit scientific action.

The source documents distinguish current configuration appearance, ordering and trace output density from shared presentation/default preferences. Follow the actual accepted configuration service and document state instead of treating every value in a settings window as a global preference. A legacy saved UI snapshot must not silently override the effective shared configuration registry.

Applying settings is different from publishing a Dataset

The documented settings window groups Display, Digitizing, Calibration, Axes & output, Dataset browser and Configurations. A page can display information or jump to a scientific editor without itself publishing an output. The final manual must reconcile the complete current menus/pages/actions in the real unchanged GUI.

The manual describes these explicit button outcomes:

  • Apply validates the tabs, commits changed shared preferences through CORE as Session overrides and saves the current Interactive Document. It stays open and reports the actual saved/error result.
  • OK applies and closes only after successful saving.
  • Cancel closes without applying the currently pending edits.

A previous successful Apply remains a committed action; cancelling a later pending draft does not imply that earlier successful saves were undone. Preserve the real save result instead of equating a closed window with success.

Invalid values or a stale shared draft are handled by the existing CORE transaction owner. Report and reconcile the actual conflict rather than privately overwriting registry state. Applying preferences does not publish a scientific Dataset or edit the source image; output names can be prepared before a separate publication action.

Notes, descriptions and structured metadata are separate

Configuration notes preserve scientific context such as legend interpretation, distortion or intentionally excluded traces. The documented publication workflow appends nonempty notes as a titled section in the published Dataset's Notes document, preserving existing content.

Publishing identical notes again does not duplicate that section. Changed notes append a new section preserving earlier published context; empty configuration notes leave existing Dataset Notes unchanged. This history is distinct from structured metadata and from a short Dataset description.

The vendor manual explicitly describes a possible partial outcome: a scientific Dataset can be published successfully while a subsequent notes update fails. Retain both facts and the actual reported reason. Do not call the scientific publication rolled back simply because its notes were not saved. Use the normal supported recovery and inspect the exact output; see per-output recovery.

Reopen the same scientific context deliberately

  1. Identify the intended Session, configuration and actual bound source.
  2. Check which shared values are inherited and which are explicit Session overrides.
  3. Inspect configuration-owned axes, accepted/active calibrations, curve identities and point ordering.
  4. Distinguish pending settings drafts from already committed saves.
  5. Select the exact published output and inspect its notes, scientific metadata and actual Dataset Preview separately.
  6. Preserve missing, changed, stale or conflicting state with its real reason rather than silently rebinding another source.

A Session change creates a different ownership context. The documented viewer protects against writing a previous Session's work into a newly selected Session. Final tutorials must demonstrate the actual save/close/reopen and Session/source handling through MAIN's allocated GUI workflow; this chapter provides no executed persistence or concurrency evidence.
