# Python/Octave Workbench extensions

Start with a working ordinary Script Workspace program using `gxtxt_api_require` and `gxtxt_api_call`. Geometry services accept execution-scoped logical handles and explicit units, never native pointers or private Dataset paths. Scientific Recipe Recorder → Export Python produces a runnable example from actual accepted operations; its public `SCIENTIFIC_RECIPE_API_v1.proposal` result is returned through `WORKBENCH_EXTENSION_API_v1.return_result`. Running it in Script Workspace stages a reviewable result without changing an unrelated open Workbench.

Open/import the identical source in Script Module Builder → Workbench extension…, choose profile W, its stable action ID/category, supported Workbench IDs and selection kinds, declare mutation and required APIs, and add shared typed fields. Build the normal ZIP, install through Plugins and enable through Configuration → Modules. Extensions… discovers the enabled compatible action; invoke it against the current logical document/selection. The source bytes remain unchanged between ordinary Workspace execution and the plugin bundle.

CORE validates plugin checksums, owner/revision, Session/resource scope, units and every requested operation. The Workbench stages its candidate geometry and applies a successful mutating result as one Undo/Redo transaction. Failed multi-operation proposals retain exact old document, geometry, history and ownership. Disabled/absent/incompatible extensions are explicit. A `return_result` proposal cannot create arbitrary filesystem files or bypass Dataset Publication. A script may separately request an explicit Dataset ID through the public Publication APIs.

See [Workbench Extension API](../api/WORKBENCH_EXTENSION_API_v1.md), [Scientific Recipe API](../api/SCIENTIFIC_RECIPE_API_v1.md), [Builder manual](../../plugins/modules/tool.script_module_builder/MANUAL.md) and final both-language coverage in [Script Bridge inventory](../api/SCRIPT_BRIDGE_COVERAGE_v1.json).
